# 系统调试

随机修复浪费时间并引入新 bug。快速修补掩盖根本问题。

## 铁律

**没有根因调查，不得提出修复方案。**

如果跳过了根因分析就提修复，那不是在解决问题，是在碰运气。

## 四阶段流程

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **仔细读错误信息** — 不跳过，不忽略。错误信息本身常包含精确解法
2. **稳定复现** — 不能稳定复现的 bug，无法确认是否修好
3. **缩小范围** — 二分法：注释代码、隔离模块、缩小到最小复现
4. **检查假设** — "这个应该没问题"往往是 bug 的来源。验证每个假设
5. **写入调试日志** — 用结构化日志追踪数据流，而不是 print 大法

### 阶段 2：确认根因

- 能用一段文字清楚描述根因吗？
- 能解释为什么这个 bug 会出现吗？
- 能预测在其他条件下也会触发同样的 bug 吗？

如果不能，继续调查。

### 阶段 3：实施方案

- 最小改动原则 — 只改有问题的代码
- 每处修改都要有理由，不能是"顺手改"
- 先写复现测试（TDD），再修代码

### 阶段 4：验证

- 测试确认已修复
- 确认没有回归
- 提交复现测试 + 修复代码

## 常见陷阱

| 陷阱 | 真相 |
|------|------|
| "这个错误很明显" | 明显的错误也有根因 |
| "先试一下这个修复" | 没有诊断的治疗是乱试 |
| "我赶时间" | 系统化调试比乱撞快 |
| "之前修过类似问题" | 症状相似不代表根因相同 |
