# 测试驱动开发（TDD）

先写测试。看它失败。写最少代码让它通过。

## 铁律

**无失败的测试，不得有生产代码。**

如果先写了代码，**删掉它**，重新来。不能保留作"参考"，不能在写测试时"借用"。

## RED → GREEN → REFACTOR

### RED — 写一个失败的测试
写一个最小测试，描述期望行为。

**好测试的特征：**
- 命名清晰描述行为
- 只测试一件事
- 不模拟不必要的东西

### 验证失败
运行测试，确认它确实因"未定义"或"未实现"而失败。
**没看到失败，就不能确定测试有效。**

### GREEN — 写最少代码
只写刚好能让测试通过的最小实现。不要多加任何功能。

### 验证通过
运行全部测试，确认全部通过。

### REFACTOR — 清理代码
保持绿色状态下改进代码质量：消除重复、改善命名、优化结构。

## 什么时候必须用 TDD

- 新功能 — 必须
- Bug 修复 — 必须（先写复现测试）
- 重构 — 必须（先有测试覆盖）

## 例外（需要用户确认）

- 一次性原型
- 配置文件
- 纯生成的代码
