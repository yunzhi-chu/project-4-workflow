# 代码审查

在问题级联之前通过审查子代理捕获问题。

## 审查时机

**必须审查：**
- 子代理开发中每完成一个任务
- 合入主分支前
- 完成主要功能后

**建议审查：**
- 遇到难题时获取新视角
- 修复复杂 bug 后

## 审查流程

### 1. 获取 Git SHAs
```bash
BASE_SHA=$(git rev-parse HEAD~1)
HEAD_SHA=$(git rev-parse HEAD)
```

### 2. 分派规格合规审查
确认代码实现了设计文档的所有要求，没有多也没有少。

### 3. 分派代码质量审查
检查：测试覆盖率、错误处理、代码组织、命名、安全性、性能。

### 4. 处理反馈

| 级别 | 处理方式 |
|------|---------|
| 严重 (Critical) | 立即修复 |
| 重要 (Important) | 继续前修复 |
| 次要 (Minor) | 记录下来稍后处理 |
| 争议 | 给出技术理由反驳 |

## 审查原则

- 审查基于工作成果，不是你思考的过程
- 子代理收到的是代码和需求，不是你的历史对话
- 发现问题 → 返回实现者修复 → 重新审查 → 循环直到通过
- 不要跳过审查因为"这只是个小改动"
